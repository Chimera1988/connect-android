# Connect 2.2.6 (16): нативные аудиозвонки

Исправления реализованы и автоматически проверены. Реальные аудиозвонки на физических устройствах ожидают приёмки.

Это отчёт об изменениях кода и доступных проверках, а не подтверждение восстановления звонков на Poco F1. Подключённых Android-устройств нет; ADB показывает пустой список. Пользователь ранее сообщил, что удалённый ADB недоступен. Успешных аппаратных логов APK → PWA, PWA → APK и APK → APK в этом окружении получить невозможно.

## База и сохранность

Основа — локальный коммит Android `c153e9fff2aff8954ab8cd469c00c8bdb8c0e2a9`, выпущенная 2.2.5 (15). Новая версия — 2.2.6 (16), `com.connect.messenger`, Android 10/API29+, ARM64 и ARMv7. Публичная старая ветка вместо этой базы не использовалась. SQLite, сообщения, медиа, WebP-стикеры, семь тем, настройки, подготовленная E2EE, Turnix и иконки не переписывались. Изменений TSX/интерфейса PWA или Android нет; встроенный интерфейс пересобран из сохранённого кода. Видеозвонков нет.

Актуальный PWA main `9d8d3b7` содержит Turnix и совместимое исправление журнала; локальная ветка отличается от него только именем уже существовавшего workflow 2.2.5. В 2.2.6 добавлены серверная SQL-функция, её изолированная проверка и установочный workflow; SDP/PWA WebRTC/TURN API не заменяются.

## A. Ошибка после ответа

По callId `326160ee-033f-46af-a0d9-48128ae9923c`, `fab39df2-f630-47d5-87d1-b133255e331e`, `4a3dd1c6-435b-4c14-b498-4be1cbe12c1d` выполнены запросы только технических признаков. Сервер подтвердил для каждого: аудио-offer, отсутствие video, answer отсутствует, 4 ICE-записи, статус declined. Содержимое SDP, сообщения и секреты не извлекались в отчёт.

Доказанный дефект `ConnectCallService.network()`: исключения в callback после проверки сервера/TURN, включая `checkAudioSdp()` и `createPeer()`, заменялись одним текстом «Не удалось открыть аудиоустройство». Это не является доказательством поломки микрофона. `createPeer()` первым вызывал `ConnectCallAudio.communication()`, который запрашивал второй AudioFocus поверх уже зарегистрированного self-managed Telecom. Отказ фокуса вызывал `IllegalStateException`, прекращая подготовку до создания answer. Этот путь согласуется с журналом и отсутствием answer.

Точный класс исторического исключения в предоставленных записях 2.2.5 не сохранялся. Без полного исключения или физического воспроизведения нельзя окончательно утверждать, что именно отказ фокуса произошёл во всех трёх вызовах. Наличие дефекта в коде подтверждено; его устранение и диагностика проверены автоматически, аппаратная первопричина остаётся для подтверждения новым журналом.

Исправления:

- `communication()` больше не запрашивает/не освобождает конкурирующий AudioManager focus и не меняет режим, принадлежащий Telecom.
- `accept()` сохраняет цепочку проверки актуального ringing-вызова → native peer → remote offer → answer → local description → ICE → атомарный серверный answer. Системный Telecom переводится в answered отдельно от пользовательского статуса разговора.
- `createPeer()` оборачивает SDP, WebRTC initialization, ADM, factory, peer и audio track в отдельные категории. ADM record/playout init/start/runtime имеют свои коды.
- `network()`, `sdp()` и `gathered()` сохраняют безопасную категорию исключения. JSONL содержит класс, первый метод Connect и строку исходника; сообщения исключений/SDP/ключи не журналируются.
- Техническая ошибка локально всегда FAILED. Серверное declined используется только для пользовательского отклонения; безопасная серверная фиксация pre-answer failure требует добавленного RPC, описанного ниже.

## B. Двусторонний RTP при оставшемся CONNECTING

В 2.2.5 независимый AudioFocus listener при LOSS_TRANSIENT устанавливал `focusAvailable=false`, отключал локальный track и блокировал `updateReadiness()`. Telecom при этом уже владел вызовом; повторного GAIN у вытесненного запроса могло не быть. Дополнительно `Connection.setActive()` ожидал пользовательского ACTIVE, который сам зависел от фокуса — образовывалась циклическая зависимость.

Исправлены `ConnectCallConnectionService.onConnectionServiceFocusGained/Lost()`, `answered()`, `ConnectCallService.applyFocus()`, `createPeer()`, `updated()` и `updateReadiness()`:

- Единственный владелец фокуса и аудиомаршрута — Android Telecom.
- Ответ в Telecom означает принятие системного вызова; надпись «Разговор» появляется только после фактической готовности звука.
- При потере Telecom focus нативная запись и воспроизведение останавливаются через WebRTC `setAudioRecording(false)` / `setAudioPlayout(false)`, track отключается. Telecom получает подтверждение освобождения ресурсов.
- При возвращении фокуса запись/воспроизведение восстанавливаются, учитывается mute. Требуются новые ADM callbacks и новые RTP-пакеты относительно сохранённых счётчиков; старые накопленные значения не считаются восстановленным звуком.
- ACTIVE требует transport connected, remote audio track, ADM recording, ADM playout, Telecom focus и двусторонний RTP. Серверный active и одно ICE CONNECTED недостаточны.
- Таймер разговора начинается при первом настоящем ACTIVE. Датчик приближения и маршрутизация сохраняются. Окончательный эффект на Poco/Bluetooth/физическом аудиовыходе не проверен.

## C. Невидимый входящий при блокировке и после разблокировки

Доказан дефект восстановления: `ConnectCallCoordinatorModule.showOnce()` зависел от активного React, текущей Activity и её фокуса, прекращал попытки через 1 секунду. `onHostResume()` запускал поиск только при idle; уже звонящий native Service повторно не показывался. Ранее onResume ошибочно записывался как фактическая видимость экрана. Входящее окно также было translucent, хотя оно рисует собственный полноэкранный фон.

Исправления:

- Новый `ConnectCallScreen` устанавливается в `Application.onCreate()` до запуска React. Сервис также устанавливает его идемпотентно. Нативные lifecycle callbacks восстанавливают текущий вызов при возвращении Activity.
- ACTION_USER_PRESENT фиксирует разблокировку, обновляет уже существующее уведомление и восстанавливает экран, когда приложение действительно находится на переднем плане. Разблокировка сама по себе не используется для запрещённого фонового запуска Activity.
- Показ входящего по full-screen PendingIntent остаётся нативным, без MainActivity/WebView/splash. При запрете автоматического показа сохраняется уведомление CallStyle с ответом, отказом и открытием экрана.
- PendingIntent имеет callId и уникальный URI. Просроченный intent не может открыть/принять следующий вызов. Дедупликация вызова, исходный deadline и рингтон при восстановлении не перезапускаются.
- `ConnectIncomingCallActivity` остаётся единственным экраном звонка. Прозрачность окна выключена для корректного перекрытия keyguard; фирменный фон и стеклянные элементы внутри Activity сохранены. `setShowWhenLocked` / `setTurnScreenOn` сохранены.
- ACTIVITY_CREATED, ACTIVITY_STARTED, ACTIVITY_RESUMED, ACTIVITY_NEW_INTENT отделены от SCREEN_VISIBLE, который требует resumed + window focus + shown decor.
- Добавлены KEYGUARD_LOCKED, DEVICE_UNLOCKED, RESTORE_PRESENTATION, NOTIFICATION_POSTED, FULL_SCREEN_INTENT_REQUESTED, PRESENTATION_DENIED. Сохраняются FCM/validation/transition/signals события прежнего формата.
- В диагностике есть включённость уведомлений, важность канала, доступность full-screen и keyguard. Если за 1,8 секунды экран не подтвердился, записывается SCREEN_NOT_CONFIRMED; отправка запроса не считается показом.

Точная причина запрета первого full-screen запуска на конкретной MIUI в старом журнале отсутствует: нет системного результата или lifecycle-логов. Исправлен подтверждённый дефект восстановления и добавлены наблюдения для определения ограничения ОС. Обход MIUI, DND и разрешений не применяется. Если пользователь запретил сами уведомления/экран блокировки, приложение не может гарантировать их показ вопреки настройкам ОС.

## Мелодия, вибрация, завершение

Встроенная Connect Call и пользовательский звук сохраняются. Единственный владелец сигналов — `ConnectCallAudio`; канал уведомлений без собственного звука/вибрации. Восстановление экрана не вызывает `incoming()` повторно. Повторяющийся шаблон и остановка на ответ/отбой/ошибку/тайм-аут сохранены. Беззвучный режим, DND и громкость Android имеют приоритет.

Сохраняется независимая очистка сигналов, peer, tracks/source, factory, ADM, WakeLock, Telecom, уведомления, таймеров. Обновлённая фиксация завершения не отправляет end-push, если RPC вернул ещё активный вызов другого устройства.

## Сервер и PWA YAML

Добавлен `connect_finish_owned_audio_call(uuid,text,text)` без изменения таблиц. Под блокировкой строки проверяются auth.uid, участник, актуальный статус и SHA-256 уже отправленного answer. Техническая ошибка записывается failed; отмена — ended по существующей семантике. Устройство без совпадающего answer не завершает активный разговор другого устройства. Секреты/SDP на сервер дополнительно не сохраняются: используется уже существующий answer, клиент хранит только его отпечаток для повторной фиксации завершения.

**В живой Supabase эта функция не установлена.** Два вызова MCP apply_migration вернули истёкшее подтверждение. Альтернативный обход прав не использовался. До применения SQL безопасная фиксация технического сбоя или отмены до подтверждения answer остаётся в очереди Android; это ограничение, а не пройденная серверная интеграция. Обычный успешный ответ и завершение подтверждённого разговора используют существующие RPC.

`Connect-PWA-Update.zip` содержит один `connect-226-call-failure.yml`. Его путь — `.github/workflows/connect-226-call-failure.yml` в `Chimera1988/connect-messenger`. Запуск при загрузке в main или workflow_dispatch. Он безопасно добавляет SQL и тест, проверяет актуальные PWA/TURN исходники, выполняет npm ci/typecheck/test/build и сохраняет исходники при доступной записи. Производственная SQL установка выполняется только при явно настроенном GitHub secret `CONNECT_SUPABASE_DB_URL` с административным подключением к нужному проекту и проверкой TLS. Без него workflow явно сообщает «Server RPC NOT applied»; один коммит SQL-файла не означает применение миграции. В архиве также есть точный SQL для администратора. Произвольная новая версия существующего RPC не перезаписывается. Откат — удалить новый RPC после остановки его использования клиентами; история не переписывается.

## Инструкция для Poco F1

1. Сохранить данные приложения, установить Connect.apk поверх 2.2.5 без удаления приложения. Проверить «2.2.6 (16)». Если Android сообщает конфликт подписи, остановиться: не удалять приложение ради установки.
2. В существующей подготовке звонков проверить микрофон, уведомления и канал аудиозвонков. На MIUI проверить разрешённость показа уведомлений на блокировке и фоновой работы. Эти системные разрешения Codex удалённо не проверял и не включал.
3. Два разных аккаунта: звонок PWA → APK с включённым экраном. Нажать «Ответить». Ожидать answer, transport/ICE connected, ADM record/playout started, focus GAIN/TELECOM, BIDIRECTIONAL_RTP и ACTIVE. Произнести разные фразы с обеих сторон. Отбой на PWA и на APK проверить отдельно.
4. Повторить PWA → APK в фоне, на блокировке и с выключенным экраном. Проверить CallStyle действия, native экран и мелодию. Если автоматический экран запрещён ОС, открыть уведомление. Пока звонок продолжается, разблокировать и вернуть Connect: должен восстановиться экран без второго рингтона и нового тайм-аута.
5. APK → PWA: после ответа ожидается «Разговор» и возрастающий таймер, оба слышат речь. Затем APK → APK, несколько последовательных вызовов, отказ, отмена, временная потеря сети и следующий звонок без перезапуска.
6. Проверить наушник/динамик/Bluetooth, mute, системную громкость, датчик приближения и остановку звука/вибрации после любого отбоя. Проверить разрешённые режимы звука/DND и свою мелодию.
7. Экспорт без ADB: настройки уведомлений → подготовка звонков → «Сохранить диагностику звонков». Для каждого результата сохранить callId, Android/MIUI, время и состояние экрана. В журнале запрос full-screen отличается от SCREEN_VISIBLE; при сбое ответа теперь есть стадия, класс, метод и строка. В чат не отправлять токены, полный SDP или ключи TURN.

## Подпись и передача исходников

Production-ключ не предоставлен. Release APK не debuggable, но подписан прежним **Android Debug fallback** сертификатом SHA-256 `fac61745dc0903786fb9ede62a962b399f7348f0bb6f899b8332667591033b9c`. Это не production-подпись. Совпадение с известным APK 2.2.5 проверяется в APK-VERIFICATION.json; установка поверх другого ключа не гарантируется. Данные сохраняются при обычном обновлении с совпадающей подписью; реальная установка не выполнена.

Android GitHub push dry-run вернул HTTP403, поэтому удалённый репозиторий **не обновлён**. Локальные коммиты и список файлов — CHANGESET.json. ANDROID-SOURCE.patch.gz предназначен строго для `c153e9f` (2.2.5). Два workflow в `android-workflows/` восстанавливают полный актуальный native исходник с SHA-проверками и могут сохранить его в GitHub при доступной записи. Они не заменяют APK. У исходной повторной сборки могут отличаться байты/подпись, но проверяемые функциональные исходники совпадают.
