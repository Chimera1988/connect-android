# Connect 2.2.7 (17): входящий вызов, экран и оповещение

Исправления реализованы и автоматически проверены. Реальные аудиозвонки на физических устройствах ожидают приёмки.

Исходная база — точная локальная версия Android 2.2.6 (16), коммит `c86bfa5776e6f1591061fb7062f4d60d3649c142`. Старый публичный Android main вместо неё не использовался. Пакет `com.connect.messenger`, minSDK29, только аудио. Выпуск предназначен для аппаратного тестирования; критерии конечной приёмки на телефонах ещё не подтверждены.

## Что подтверждено и что нельзя считать подтверждением

Пользователь сообщил о реальных успешных цепочках 2.2.6: ICE CONNECTED → BIDIRECTIONAL_RTP → AUDIO_READINESS READY → ACTIVE. Это сохранённая исходная функциональность, а не результат нашего аппаратного теста 2.2.7. Пользователь также сообщил об отсутствии экрана на Android10/Poco F1 и Android15 при доставленном FCM. Мы не относим всю неисправность к MIUI.

В 2.2.6 `FULL_SCREEN_INTENT_REQUESTED` показывал запрос, а `NOT_FOREGROUND` относился к отдельному прямому запуску Activity. Эти события не доказывают, что Android отказал full-screen уведомлению. Нет системного WindowManager/SystemUI trace конкретных телефонов: точную причину каждого решения ОС нельзя восстановить из старого JSONL.

Ниже перечислены устранённые дефекты фактического кода и последовательности действий. Автоматические тесты проверяют их, но не подтверждают пробуждение экрана, физическую вибрацию или голос на Android10/15.

## Исправленные причины

### 1. Входящий создавался обновлением уже существующего тихого уведомления

До исправления `onStartCommand()` вызывал `startForeground()` с ID `0x434f4e`, без CallStyle/FSI. После серверной проверки `showNotification()` обновлял тот же ID до входящего. Таким образом, новый вызов мог попасть в путь обновления уведомления вместо пути добавления нового срочного события. Последующие profile updates и `incomingPosted/setOnlyAlertOnce` дополнительно усложняли диагностику.

Теперь:

- `startBootstrap()` выполняет обязательный ранний foreground старт отдельным ID `0x434f4f` и отдельным LOW-каналом `connect-native-call-bootstrap-v1`. Это служебное уведомление категории SERVICE, без рингтона и FSI.
- Первый входящий CallStyle публикуется как новая запись ID `0x434f4e` на существующем HIGH-канале звонков `connect-native-calls-service-v6`. После продвижения foreground service первоначальная служебная запись удаляется.
- Первый CallStyle содержит собственные answer/decline/open PendingIntent и full-screen intent, когда он разрешён. Для срочного вызова явно указан FOREGROUND_SERVICE_IMMEDIATE.
- `ConnectIncomingAlerts` отделяет разрешение презентации Telecom, первую публикацию и однократный запуск сигналов. Bootstrap не может пометить входящий уже показанным. Повторные FCM/onShow/profile updates не запускают второй рингтон и не сбрасывают deadline.
- У обновлений стоит onlyAlertOnce, но тот же full-screen PendingIntent сохраняется, пока звонок входящий. Это защищает от гонки, когда быстрое обновление пришло раньше обработки первой записи SystemUI. После ответа full-screen intent удаляется вместе со входящим стилем.
- Очистка удаляет только оба ID звонковой службы; уведомления сообщений не затрагиваются.

Существующий пользовательский канал не удаляется и его важность не переписывается. Создаётся только отдельный тихий технический канал. Высокая важность и разрешённый FSI остаются условиями, а не гарантией решения SystemUI.

### 2. Callback Telecom не вызывал презентацию

`ConnectCallConnectionService.onShowIncomingCallUi()` содержал пустой обработчик. Теперь он передаёт callId единственному `ConnectCallService.presentIncoming()`. Публикация собственного входящего UI и запуск оповещения происходят после разрешения Telecom, без React/WebView.

`onCreateIncomingConnection()` и исходящий counterpart фиксируют создание Connection. Ошибки создания извлекают callId как из прямых, так и из вложенных extras и завершают именно свой вызов. Если Telecom выбирает собственный UI из-за конкурирующего разговора, отсутствие onShow не используется как повод обойти его решение. Через 2,5 секунды ожидание callback логируется как SYSTEM_UI_OR_PENDING, а не успешный показ. Серверный TTL и проверка окончания продолжают работать.

`onSilence()` теперь останавливает входящее оповещение по явному запросу Telecom. Ответ, отказ, abort и disconnect продолжают управлять тем же объектом вызова. Если регистрация/добавление в Telecom реально выбросили исключение, оно журналируется отдельно; ранее исключение только скрывалось в Logcat.

### 3. PendingIntent для Android15+

Целевой SDK приложения выше35. У создаваемого PendingIntent отсутствовал явный creator opt-in для фонового запуска Activity, предусмотренный Android15. В `ConnectCallScreen.pending()` добавлены публичные ActivityOptions для SDK35+; на SDK36 используется соответствующий явный режим. Опции применяются только к неизменяемым PendingIntent, направленным на конкретную неэкспортируемую ConnectIncomingCallActivity, с callId и уникальным URI.

Приложение не вызывает PendingIntent.send() из фона и не запускает MainActivity/WebView как замену full-screen механизму. Разрешение USE_FULL_SCREEN_INTENT и проверка canUseFullScreenIntent сохранены. Эти опции не обходят запрет ОС и не доказывают, что отсутствие opt-in было единственной причиной на конкретном Android15; это исправленный пробел совместимости.

Фоновая невозможность прямого запуска теперь записывается как `foreground-presentation / DEFERRED / NOT_FOREGROUND`. Она не объявляется отказом уведомлению. При возвращении Connect на передний план сохраняется нативное восстановление актуального входящего без нового вызова/рингтона/таймера.

### 4. Начальное событие фокуса останавливало рингтон

Подтверждённая пользователем цепочка `ringtone PLAY_REQUESTED → focus TRANSIENT → signals stopped` совпадала с `applyFocus(false) → sounds.stopSignals()`.

Теперь `applyFocus()` управляет только готовностью и записью/воспроизведением WebRTC. Во входящих PRESENTING/INCOMING он не останавливает мелодию и вибрацию; фиксируется RINGING_FOCUS_INDEPENDENT. Гудки/сигнал разговора отделены методом stopTone(). Входящее оповещение останавливается при ответе, отказе, завершении, тайм-ауте, очистке службы или явном Telecom onSilence. Разговорный AudioFocus остаётся у Telecom, второй AudioManager focus не добавлен.

### 5. Встроенный и пользовательский рингтон

RingtoneManager.getRingtone мог скрывать резервное системное воспроизведение при проблемном URI. Вместо него используется один асинхронный MediaPlayer с USAGE_NOTIFICATION_RINGTONE, системной громкостью звонка и looping. Встроенный WAV Connect Call сохранён байт в байт, находится в APK без сжатия и работает без сети.

Проверка выбранного URI, создание player, prepareAsync, начало и isPlaying различаются в JSONL. Ошибки URI_ACCESS_DENIED, URI_NOT_FOUND, CUSTOM_URI_INVALID, PLAYER_CREATE_FAILED, PLAYER_PREPARE_TIMEOUT, PLAYER_START_FAILED и коды Android player отделены от DND/беззвучного режима/нулевой громкости. Из журнала исключены URI/имена файлов и сообщения исключений.

Если свой файл недоступен, выбирается только встроенная Connect Call, с FALLBACK_REQUESTED и явной надписью в экране/уведомлении/подготовке звонков. Выбор не стирается молча; повторный выбор или возврат к Connect Call очищает предупреждение. Случайный системный рингтон и звук сообщений не используются.

Выбор файла уже копировался в принадлежащую приложению MediaStore-запись; временное разрешение внешнего document provider после копирования не требуется. Существующие URI и настройки не мигрируются/не удаляются. Фактическая доступность после перезагрузки и воспроизведение на телефонах остаются в аппаратной матрице.

ConnectRingLease запрещает запоздавшему onPrepared/error callback включить звук после отбоя или во время следующего вызова. Ошибка вибратора больше не прерывает создание независимого аудиоплеера. Ошибка аудиофайла не прекращает разрешённую вибрацию.

### 6. Неоднозначная проверка вибрации

Раньше одна запись VIBRATION_DISABLED объединяла выключенный флаг Connect и `Settings.System.vibrate_when_ringing == 0`. Устаревший ключ проверялся и на SDK35, где он не является надёжным единственным источником настройки звонковой вибрации. Из старой записи нельзя определить, какое условие сработало у пользователя.

Теперь различаются CONNECT_VIBRATION_OFF, NO_VIBRATOR, RINGER_SILENT, SYSTEM_RING_VIBRATION_OFF, SYSTEM_RING_INTENSITY_OFF, DND, VIBRATE_PERMISSION и VIBRATOR_ERROR. На SDK29/30 учитывается доступный старый переключатель; отсутствие OEM-настройки не приравнивается к выключению. На SDK31+ устаревший ключ не блокирует запрос. Доступная нулевая системная интенсивность уважена; окончательную политику определяет Android.

На SDK33+ используется VibrationAttributes.USAGE_RINGTONE, на старых версиях — соответствующий AudioAttributes. Шаблон 450мс/850мс повторяется до остановки. На новых устройствах берётся defaultVibrator из VibratorManager. Настройка Connect сохраняется; явно выключенный пользователем флаг не включается принудительно. Публичный Android API не даёт подтверждения физического движения мотора: PATTERN_REQUESTED означает запрос, не аппаратный успех.

## Первоначальная настройка и разрешения

Существующая страница подготовки звонков обновлена до setupVersion17 и один раз повторно показывает проверку после обновления. Она проверяет микрофон, уведомления, важность конкретного звонкового канала, доступность FSI на SDK34+, регистрацию PhoneAccount и isIncomingCallPermitted, режим/громкость звонка, DND, причину политики вибрации и ограничение батареи.

Ссылки ведут в настройки звонкового notification channel, полноэкранных уведомлений, фоновой работы/батареи и приложения. Нужные каналы создаются до проверки готовности. Нет новых разрешений чтения файлов, контактов, телефонного состояния, overlay или скрытых разрешений. На Android10 не запрашиваются POST_NOTIFICATIONS/специальный доступ Android14. Автозапуск/фоновые ограничения MIUI объясняются как дополнительные настройки производителя, а не универсальная причина неисправности Android15.

## Что сохранено

Не менялись PWA и серверный протокол, Turnix/ICE endpoint, SDP/ICE очередь, Opus, factory/ADM, критерии двустороннего RTP, AudioGate и переход в ACTIVE. Отбой, серверная синхронизация и guard владения answer из2.2.6 сохранены. Кратковременный ICE disconnect сохраняет предусмотренный путь RECONNECTING; тайм-аут не заменён немедленным отбоем.

FCM native receiver/service, high-priority обработка, хранение токена/сессии, повторная регистрация, серверная валидация и защита от дублей не переписывались. DUPLICATE не считается ошибкой при обработанном первом событии. Force-stop Android по-прежнему ограничивает FCM до запуска пользователем; обходов нет.

Сообщения, SQLite, кеш, стикеры, медиатека, контакты, семь тем, подготовленная E2EE и SVG/фирменные ресурсы не менялись. Встроенный веб-интерфейс пересобран с тем же содержимым. Новый YAML для PWA не требуется и не поставляется; существующая серверная конфигурация не изменялась этим выпуском.

## Диагностика

Сохранён JSONL-формат и экспорт безADB. Категории FCM/server validation/transition/SDP/ICE/transport/ADM/RTP/readiness/finish/cleanup продолжают работать. Добавлены:

- Telecom connection created/failed, ON_SHOW_INCOMING_CALL_UI, UI_CALLBACK_PENDING.
- BOOTSTRAP_POSTED, FIRST_CALL_POST_REQUESTED, CALL_UPDATE_REQUESTED и ID двух уведомлений.
- Проверка NotificationManager.activeNotifications через400мс: NOTIFICATION_REGISTERED/NOTIFICATION_NOT_REGISTERED, наличие FSI и интерактивность/keyguard. Регистрация уведомления не равна экрану.
- FULL_SCREEN_INTENT_REQUESTED и отдельно ACTIVITY_CREATED/STARTED/RESUMED/SCREEN_VISIBLE. SCREEN_VISIBLE требует window focus и показанного decor. VISIBILITY_UNCONFIRMED не притворяется системным отказом; ОС могла выбрать heads-up/свой UI.
- PLAY_REQUESTED/PLAYING/FAILED/FALLBACK_REQUESTED, точная причина stop; vibration request/suppression/failure.
- User-action на входе в единственный native controller.

CallId и operationId по-прежнему связываются через переход создания исходящего. Токены, SDP, ICE-адреса, ключи TURN, сообщения, имена контактов и аудио в отчёт/диагностику не добавляются.

## Как принять на телефонах

1. Установить Connect.apk поверх2.2.6, без удаления данных. Проверить2.2.7(17). Если Android сообщает несовпадение подписи, остановиться и не удалять приложение ради обновления.
2. В подготовке звонков проверить микрофон, разрешения, канал звонков, FSI и системные режимы. Новые разрешения за пользователя не включаются. Для чистого теста разрешить необходимые стандартные доступы, обычную громкость звонка и вибрацию, выключить DND.
3. С двумя аккаунтами выполнить PWA iPhone → APK на включённом экране, затем на заблокированном/выключенном. Новая ожидаемая цепочка: FCM → CALL_VALIDATED → Telecom INCOMING_CONNECTION_CREATED → ON_SHOW_INCOMING_CALL_UI → FIRST_CALL_POST_REQUESTED → NOTIFICATION_REGISTERED → возможный ACTIVITY_* → SCREEN_VISIBLE. Отдельно проверить PLAYING и PATTERN_REQUESTED, а физически — слышимость и вибрацию. Когда экран включён и другое приложение открыто, ОС вправе выбрать heads-up с действиями.
4. Принять из уведомления и из native UI. Ожидать answer/ICE/transport/ADM/bidirectional RTP/readiness/ACTIVE; проверить разные произнесённые фразы с обеих сторон, mute, выходы звука, громкость и proximity. Отбой на каждой стороне, следующий вызов без перезапуска.
5. Проверить свой файл после перезапуска/перезагрузки; удалить скопированный файл в MediaStore и проверить явное предупреждение и встроенную резервную мелодию. Режимы DND/без звука/нулевая громкость не считать неисправностью, если подавление разрешено политикой.
6. Повторить направления APK → PWA и APK → APK, фон, Doze, удаление из недавних, восстановление процесса и разные сети/TURN. Для каждого записать модель/API/состояние, два аккаунта без секретов, время, callId, фактический показ/звук/вибрацию и способ ответа.
7. Экспорт: настройки уведомлений → подготовка звонков → «Сохранить диагностику звонков». В новых логах NOT_FOREGROUND не означает отказ FSI, а PATTERN_REQUESTED не означает проверенную работу мотора. Без аппаратной приёмки выпуск нельзя объявлять окончательно восстановленным.
