# Connect Android — итог аудита PWA parity и подготовка выпуска

Дата: 2026-11-19 UTC. Работа выполнена одним агентом. **Это проверенные изменения исходников и процедура релиза, а не заявление о полном 100% parity или готовом проверенном на телефоне APK.** Новый production APK/OTA не опубликован. Нативная компиляция и аппаратная приёмка остаются незавершёнными.

## Источники и границы

## Подтверждённые исправления

1. Актуальная server verification и seamless session PWA перенесены в Android: periodic/focus/network recheck не сбрасывает открытый проверенный чат; confirmed 401/403 закрывает UI.
2. Logout блокирует UI сразу и имеет persistent native/WebView network fences. Старый токен в памяти не позволяет продолжить отправку через эти клиенты; запоздалый native refresh не сохраняет токен после lock. Очистка SQLite выполняется пока ещё существует authenticated owner, после чего удаляются обе копии persisted session. FCM deregistration имеет ограниченный timeout и использует отдельно захваченные прежние credentials только для DELETE регистрации.
3. Исправлены группировка и скругления настроек для обеих ролей; добавлен отсутствовавший экран администратора Storage/Database/Traffic с существующим endpoint и без выдуманного egress.
4. Большие фотографии Android теперь используют тот же bounded optimizer перед single upload и album upload, сохраняя alpha/original fallback. Кодеки нативных записей не заменены браузерной имитацией.
5. Версия установленного APK берётся из Android PackageManager новым `getAppIdentity`. Это устраняет подмену установленного build номером OTA manifest и ошибки проверки доступности APK обновления.
6. Release plugin больше не подписывает release debug-ключом при отсутствии production key: получается unsigned build для проверок, а выпуск требует явной подписи и проверки сертификата.
7. Добавлен один компактный release workflow и версионируемые release scripts. Проверки не меняют исходники/версии и не выполняют push или backend migrations.

Supabase signOut не делает уже выданный JWT мгновенно недействительным на произвольном внешнем клиенте: это ограничение протокола, а не обещание глобального отзыва. Здесь блокируются оба клиента Connect и их persisted state; серверные схемы/TTL не менялись. Для границ auth сверены установленный supabase-js/Auth JS и текущая документация signOut.

## Как читать матрицу

Пути PWA относительны корню connect-messenger; Android — native/. `соответствует` означает совпадение подключённого производственного пути и указанную автоматическую проверку, **не** физический end-to-end тест. Для серверного RLS/двух аккаунтов и аппаратных функций доказательств меньше — это отмечено отдельно. Ссылки на тесты — файлы native/tests, если не указан другой путь.

3. Для этой версии сначала **apk**. `previous_release=connect-android-v3.0.7-b25`. В environment `production` должны быть существующие `CONNECT_RELEASE_KEYSTORE_BASE64`, `CONNECT_RELEASE_STORE_PASSWORD`, `CONNECT_RELEASE_KEY_ALIAS`, `CONNECT_RELEASE_KEY_PASSWORD`. Keystore должен иметь указанный production certificate. Без него job останавливается; нового ключа, debug fallback и force push нет. Version/code уже 3.0.8/26 в исходниках; workflow их не меняет.
4. APK job проверяет предыдущий реальный APK, строгое увеличение code, production certificate и результат. Затем публикует GitHub Release tag `connect-android-v3.0.8-b26` с **Connect.apk**, SHA256, APK verification, native baseline и отчётом; этот формат понимает существующий in-app updater. Те же файлы лежат в `connect-apk-result-<run_id>` artifact. Одновременные production jobs сериализованы.
5. Установить APK26 через системный installer **поверх** совместимо подписанного APK25; не удалять приложение, не очищать storage. Сверить SHA256 и signer до установки. После установки проверить session/profile/settings/локальный кэш и сообщения; затем пройти CSV на Poco F1/API29 и современном Android. Автоматическая сборка не заменяет этот этап.
6. Только после установки/приёмки новой базы выбирать **ota**, указав `previous_release=connect-android-v3.0.8-b26`. Требуется `EXPO_TOKEN` в production environment. Workflow скачивает CONNECT-NATIVE-BASELINE.json из уже опубликованного APK-release, сравнивает runtime/native digest/project/channel/certificate, проверяет EAS identity, active production channel и production public configuration. Далее `eas update --channel production --platform android --environment production` (CLI27.10.0), только после verify job. Результат: `connect-ota-result-<run_id>`, update ID/group/URL и Summary.
7. **OTA для APK25/v1 запрещена этим guard.** У APK25 нет нового getAppIdentity. Если baseline отсутствует/другая или поменялись native plugins/dependencies/permissions/resources, сначала новый APK и при несовместимости новый runtime. Workflow не делает автоматический remap production channel и не исправляет версии во время запуска.
8. В приложении: Настройки → О приложении → проверить установленную версию (PackageManager), отдельно OTA/runtime и состояние обновления. Применять OTA по кнопке после звонков/записи/передач; обычный ON_LOAD с timeout0 загружает в фоне, может потребоваться до двух холодных запусков. Не удалять данные для проверки обновления.

### Безопасный rollback OTA

Автоматического отката без выбора проверенной версии нет. Сохранить `ota-publication.json` и compatibility evidence успешного запуска. Перед откатом проверить `eas update:view <group> --json`: тот же EAS project, Android, runtime и прежняя принятая native baseline. Затем авторизованным EXPO_TOKEN выполнить `eas update:republish --group <проверенный_group_UUID> --destination-channel production --platform android --message 'Rollback to verified group' --non-interactive --json`, сохранить новый group/URL. Это новая публикация проверенного JS, а не downgrade APK. Нельзя переносить v1 group на v2 в качестве восстановления нового native API.

## Остаточные ограничения и критерии приёмки

Полный parity **не подтверждён**: импортированные видео/WAV не имеют нового native transcoder; Android explicit-tap video отличается от PWA autoplay; полное удаление всех локальных byte caches при смене аккаунта не доказано; пиксельная приёмка всех тем, live backend/RLS, FCM, APK↔PWA audio, датчики, Doze и установка без потери данных требуют устройства/аккаунтов. Эти пункты не выданы за успешные. Исправления исходников и новый компактный workflow существуют, но готовый проверенный production APK отсутствует до успешного CI и аппаратной приёмки.
